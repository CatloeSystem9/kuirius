# Goal Continuity v1 — Implementation Plan

## Context

Krisha can execute tasks and track projects, but nothing persists a user *objective* across sessions: restart loses intent, unfinished work is forgotten, and the user must re-explain context. This task adds a persistent, lightweight, event-driven goal-continuity subsystem that reuses the existing agent infrastructure (no duplicates), preserves user control, and passes the full regression suite.

**Architecture inspected (evidence base):** browser-side agent runtime composed in `src/agent/bridge.ts` `createAgentSystem()`; every subsystem follows the same conventions — `StorageAdapter` injection, `{ schemaVersion }` envelopes, repair-don't-drop loading, hard caps with deterministic eviction, synchronous write-through, never-throw, event-driven `attach(bus)` (no polling). Key reusable pieces: `MemoryService.remember/recall/update/forget` + metadata-marker ownership (`projectEngine.ts:390-404` pattern), `KnowledgeGraph` with existing `EntityType 'goal'` and relationships `related_to/blocks/supports`, `ProjectEngine.profile/listProfiles` + `PROJECT_STATUS_UPDATED {forgotten:true}`, `SkillEngine.match()` (verified-only), `LongRunManager` TRANSITIONS table precedent (`sessionTypes.ts:41-57`), `similarity()` (`memory/similarity.ts`, Jaccard+containment), tool pattern from `projectTools.ts`, diagnostics passive-check pattern (`intelligenceChecks.ts:278-323`).

**Key integration discovery:** `App.tsx:1447` posts `getMemoryService().recall(text, {limit:8}).map(m => m.content)` to `/api/chat` — so compact goal mirror records in MemoryService surface in chat context automatically through the existing relevance-ranked recall path. Zero `server.ts` changes needed; resumption intelligence rides existing retrieval. Goal nodes/edges in the KnowledgeGraph surface in agent-task context via the existing `queryStatements` path.

## Design decisions

1. **New subsystem `src/agent/goals/`** (GoalEngine), constructed in `bridge.ts` after `projects`/`skills`, exposed as `AgentSystem.goals`, attached like `ConsolidationEngine`. Persists under storage key `krisha_goals_v1`, `GOALS_SCHEMA_VERSION = 1`, cap `MAX_GOALS = 24`.
2. **Lifecycle** (transition table copied from the long-run precedent): `PROPOSED → [ACTIVE, COMPLETED, ABANDONED]`; `ACTIVE → [PAUSED, BLOCKED, COMPLETED, ABANDONED]`; `PAUSED → [ACTIVE, BLOCKED, COMPLETED, ABANDONED]`; `BLOCKED → [ACTIVE, PAUSED, COMPLETED, ABANDONED]`; `COMPLETED`/`ABANDONED` terminal. Invalid transitions rejected safely, never guessed.
3. **GoalRecord**: unique id (`goal_` + timestamp/base36, assigned once — stable thereafter), description ≤200 chars, status, `originMessage` ≤160 chars (provenance snippet only — never conversations), milestones ≤20, `progress { completed[], remaining[], blockers[] }` ≤10 items each (mirrors `ProjectDevStatus` shape), `projectRefs[]` ≤3 (approved roots only), `blockedByGoalIds[]`, `lastActivityAt`, `lastBriefedAt`, timestamps.
4. **Intent detection is deterministic and conservative** (`goalIntent.ts`, MEMORY_PATTERNS-style regexes): explicit commitment ("let's build…", "I want to…") creates **active** goals; vague/hypothetical ("maybe…", "what if…", "thinking about…") is ignored; soft intent ("I was considering…") creates **proposed** goals that require explicit confirmation ("yes / go ahead / confirmed" after a briefing) — never silently reinterpreted. Pause/resume/complete/abandon recognized only from explicit statements matched to an existing goal by `similarity() ≥ 0.62`.
5. **Deduplication**: new goal statements are compared against non-terminal goals via `similarity()` (threshold 0.62, same as consolidation) — matches update the existing record (refine description, bump timestamps, keep id); terminal goals are never resurrected (a new similar statement creates a fresh goal).
6. **Resumption, never execution**: `resumptionBriefing(input)` ranks active/paused/blocked goals by similarity to the current input, includes completed-so-far / remaining / blockers / project refs / optional verified-skill hint; emits `GOAL_RESUMPTION_BRIEFED`; rate-limited via `lastBriefedAt`. The engine NEVER calls tools or executes anything — resuming means restoring context and proposing the next step.
7. **Surfacing without UI changes**: memory mirror (one compact `[goal <id8>] …` record per goal, updated on transitions, released on forget — marker `metadata.goalId`) → surfaces in chat via existing recall; graph mirror (`type:'goal'` nodes + `related_to` project edges + `blocks` edges, snapshot-based prune copied from the just-fixed ProjectEngine pattern incl. `getAllEdges(limits.maxEdges)`) → surfaces in agent context; `goal.*` tools for explicit queries. No new rendering anywhere.
8. **Skills**: briefing hint only — `skills.match(goal.description)` where `score ≥ 0.6 && blockers empty` (verified+active only); never executed.

## Safety & performance guarantees

- No polling/timers/network/embeddings: pure local regex + bounded similarity scans (≤24 goals × short strings), event-driven only; lazy storage load, no startup cost.
- Goals never trigger actions; all mutations exposed as gated registry tools; emergency stop blocks non-`safe` goal tools (existing gate semantics untouched).
- `forget()` releases only records carrying the engine's own `metadata.goalId` marker — unrelated memories never deleted (ProjectEngine-proven pattern).
- Persistence across reloads via the shared StorageAdapter; nothing auto-runs on restart; corrupted/future storage → clean start, never throws.
- Stale project references cleared on `PROJECT_STATUS_UPDATED {forgotten:true}` + lazily revalidated against approved profiles.
