# Local Private Vault (LPV) — Revised Implementation Plan (hardened)

## Context

Krisha (React 19 + Vite + Express + TypeScript, Windows-only) needs a net-new post-roadmap capability: an encrypted local-only vault for credentials with category-based retention, controlled retrieval, audit, and a management UI. Your decisions: **browser (CDP) fill only**; **locked after every restart + auto-lock**. Your six hardening directives are incorporated verbatim below (each mapped to a concrete mechanism). SPF stays out of scope (seam only).

Investigation findings (recap): E5 protected store `C:\ProgramData\Krisha\sandbox` (full) / `%LOCALAPPDATA%\Krisha\sandbox` (degraded) is already outside every model-writable root, refused to the fs agent (`assertNotProtected`, `fsSearch` skip), never OneDrive-synced (repo itself is under OneDrive — vault stays out of cwd). Reusable: `durableWrite`, hash-chained audit pattern, `enforce()`/`ENFORCED_ROUTES`, scoped server permission grants, approval-card UI pattern (`RollbackApprovalCard.tsx`), modal CRUD pattern (`MemoryModal.tsx`), standalone test suites (`scripts/test-e5-m1.ts:60-72` env-isolation pattern). No DPAPI usage exists yet; Node `crypto` is the crypto substrate; no new npm dependencies.

## Design — keyed to your six directives

### 1. Master-key handling (`lpvDpapi.ts` + `lpvCore.ts`)
- Master key = `crypto.randomBytes(32)`, generated once at first init; wrapped with **DPAPI `DataProtectionScope.CurrentUser`** and stored base64 in `lpv/key.blob` (keys separate from data). Unwrapped **only inside the unlock flow**.
- **Dedicated DPAPI worker**: a separate persistent PowerShell process owned solely by `lpvDpapi.ts` (own spawn, own queue, own line protocol). The existing mouse/keyboard worker in `server.ts` is **not touched and not shared** — server.ts keeps its own worker entirely unchanged.
- While locked: no unwrapped key exists in memory. On `lock()` and after every completed operation the master key, HKDF-derived subkeys, and decrypted payload Buffers are **zero-filled** (`buffer.fill(0)`) — secrets are held as Buffers, never as long-lived strings; fill responses/audit/logs never carry them.
- **Account binding**: at vault init the dedicated worker returns `[System.Security.Principal.WindowsIdentity]::GetCurrent().User.Value` (SID); stored in `lpv/account.json`. Every unwrap compares the current SID; mismatch → refuse (fail-closed) + `lpv_key_unwrap_denied` audit event. DPAPI itself additionally fails if the blob moves off-account.
- DPAPI unavailable (no .NET ProtectedData) → vault refuses to initialize (fail-closed). Implementation step 1 verifies a DPAPI protect/unprotect round-trip on this machine.

### 2. Credential-fill authorization (stricter)
- No endpoint anywhere returns a secret. The only retrieval path is `POST /api/vault/fill {entryId, fields:[{secret:'username'|'password', match}]}` — decrypt → CDP type → zero buffers → respond `{success, filled:[{field, matchedFieldLabel}], url}` metadata only.
- Grants are **single-use (consumed on first use), ≤60 s TTL, and bound to the tuple {entryId, operation:'fill', approved origin}**. Issued only as server-minted records after explicit user approval (UI fill click, or approval challenge for automation — approved solely via the UI card; the model can never self-grant).
- **Origin verification before filling**: server reads CDP page state and refuses unless the top-frame URL origin equals the approved origin. A grant for one entry/origin is useless for any other entry or site.
- **Field verification**: the password field must be a visible `input[type=password]`; the username field a visible text/email/tel input. Prevents typing a secret into search/message boxes (exfiltration pattern).
- **Navigation/frame rejection**: iframes are ignored (top frame only); if the page navigates mid-fill or the URL changed between the pre-check and post-fill check, the operation fails and is not retried; refusal is audited (`lpv_fill_refused` with reason kind).
- Match specs are validated and bounded; page-matching cannot be generalized into credential access — there is no "get secret" or "read field" mode.

### 3. Vault integrity (`lpvCore.ts`)
- **HKDF domain-separated subkeys** from the master key: `enc` (per-entry AES-256-GCM, random 12-byte IV, AAD = `{id, categoryKey, updatedAt}`) and `mac` (**HMAC-SHA256 over the canonical full vault document — policy and plaintext metadata included**). The self-hash is replaced by this keyed MAC; accidental *and* deliberate modification are detected.
- MAC is verified **at unlock, before any operation is permitted**; failure → vault enters `TAMPERED` fail-closed state (no read/write/fill; nothing recreated or reset — ever). Operator-only recovery: UI "restore previous generation" re-verifies the MAC of `vault.json.bak`, or documented manual reset.
- **Generation tracking**: monotonic `generation` counter incremented by every mutation; `.bak` always holds generation−1; non-monotonic or inconsistent generations → `TAMPERED`.
- **Audit chain**: LPV audit (`lpv/audit/lpv-audit.jsonl`, hash-chained + fsync-per-entry, E5 pattern) is **fully chain-verified before the history endpoint serves it**; a broken/lost chain is served marked `untrusted` and continued only with an explicit `lpv_audit_chain_restarted` marker (never silently).
- Persistence: `durableWrite` (temp→fsync→rename) for every byte; vault bytes live only in `lpv/` under the E5 protected store (also covered by `appendAuditSyncSafe` into the main E5 audit for authority transitions).

### 4. Degraded mode (stricter)
When storage protection is `degraded` or `unavailable`: **all vault writes refused (save/update/delete/policy), auto-saving disabled, unlock, retrieval and fill refused**. Only status, metadata list and audit history remain readable so the operator can see state; the status banner shows the degradation. Nothing quietly weakens guarantees to stay available; protection restoration re-enables operation (re-evaluated per operation via `getStorageInfo()`).

### 5. Precise auto-lock
- Lock after **5 min without authorized vault activity** (configurable `autoLockMs`): the idle timer is reset **only** by unlock, mutations (save/update/delete/policy) and approved fills — **read-only polls/status/entries listing never reset it**.
- **In-flight fill completes before locking**: a fill holds an operation guard; auto-lock defers until it finishes (fills are bounded ≤10 s; lock state is re-checked at fill start and completion).
- **Lock on shutdown**: SIGINT/SIGTERM/beforeExit handler zeroes key material and records the locked state; boot is always locked regardless.
- **Defense in depth**: lock state is enforced both in the `ENFORCED_ROUTES` handlers and again inside `lpvCore` — a locked vault refuses every retrieval and fill path (metadata list and audit history remain available).

### 6. Retention detection (fail-closed)
- **Category A** (approval required, never auto-saved): built-in `google`, `email_primary`, `banking`, `payment`; **every unclassified/user-defined category defaults to A**.
- **Category B**: only categories the user explicitly enables in `policy.autoSaveCategories` (master toggle + per-category, disable anytime).
- **Category C — explicit rejection table**: field labels/titles matching otp, one-time password/code, verification code, security code, cvv/cvc/cvv2, 2fa/authenticator code, totp seed, temporary/temp code; plus shape rules (6–8 digit value in a code-labeled field; base32 TOTP-seed shape in a secret/key/seed-labeled field). **Any uncertain match → refuse the save (fail-closed)** with a clear reason; heuristics are documented as best-effort — never claimed to catch every OTP.

## Server surface (all `stopBlock:true`, rate-limited, permission-gated)

`GET /api/vault/status` (public status: initialized/locked/protection/categoryCount) · `GET /api/vault/entries` (metadata only, `vault.manage`) · `POST/PUT/DELETE /api/vault/entries` (`vault.manage`; PUT/DELETE also in-degraded-refused) · `GET/PUT /api/vault/policy` · `GET /api/vault/history` (MAC/chain-verified, `vault.manage`) · `POST /api/vault/lock` · `POST /api/vault/unlock` · `POST /api/vault/fill` (`vault.retrieve` + single-use bound grant) · `GET /api/vault/approvals/pending`, `POST /api/vault/approvals/{approve,decline}` (challenge lifecycle, UI-only approval). `SERVER_SESSION_SEED` gains `'vault.manage': true` (operator baseline), `'vault.retrieve': false`.
