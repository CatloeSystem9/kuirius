## 1. Approval authorization model

**Implementation:** approval tokens are generated with `crypto.randomBytes(24).toString('hex')` — cryptographically unpredictable. Tokens are single-use, 5-minute TTL, bound to `{path, mtimeMs, size, classification}`.

**Verified guarantees:**
- Tokens cannot be generated by the malware-detection model (no model has token-generation capability; the route requires `application.launch` server permission).
- Tokens are bound to the exact process identity (path + mtimeMs + size match enforced at validation).
- Tokens are single-use (consumed atomically in the synchronous validation path).
- Tokens expire after 5 minutes.
- Tokens cannot be replayed after server restart (in-memory only, not persisted).
- Concurrent requests cannot consume the same token twice (Node.js single-threaded event loop; the check-and-consume is synchronous).
- Approval cannot override E-stop (checked before token validation and again before termination).
- Approval cannot override CONFIRMED_MALWARE (`issueApproval` returns null).

**Limitation (documented):** there is no operator identity authentication — any caller with `application.launch` server permission can request an approval token. The token proves "someone with launch permission approved this specific executable at this specific identity" but does not prove WHICH operator approved it. This is consistent with the existing Phase 18 architecture (which also uses permission-based rather than identity-based authorization) and is disclosed as a known limitation.

## 2. Process identity and PID reuse

**Implementation:** containment verifies the target process via WMI `Win32_Process` query. The verification checks:
1. Process exists (null → ALREADY_EXITED)
2. Creation time matches the evidence (mismatch → REFUSED_PID_REUSED)
3. Executable path matches the evidence (mismatch → REFUSED_IDENTITY_CHANGED)
4. Process name matches the evidence (mismatch → REFUSED_IDENTITY_CHANGED)

**PID-reuse protection:** Windows assigns PIDs sequentially and reuses them after the original process exits. The creation-time check prevents terminating a different process that reused the same PID. If a PID-reused process has a different creation time, containment is refused with `REFUSED_PID_REUSED`.

**Test coverage:** PID-reuse rejection, creation-time mismatch, executable-path mismatch, process-name mismatch — all tested and passing.

## 3. Evidence freshness policy

**Policy:** containment evidence must be <24 hours old from the Phase B assessment timestamp. Stale evidence is refused with `REFUSED_STALE_EVIDENCE`.

**Freshness is combined with identity verification:** the 24-hour timestamp does NOT substitute for identity verification. Even with fresh evidence, the process identity is revalidated via WMI immediately before termination. The freshness check prevents acting on outdated classification results; the identity check prevents terminating the wrong process.

**Limitation:** a 24-hour window means the executable file could have been replaced within that period. The file identity check (mtime + size via `statFile`) partially addresses this, but a sophisticated replacement that preserves mtime and size would not be detected. Full protection requires hash-based identity verification at launch time (Phase C integration).

## 4. Termination race and safety

**Intended sequence:** Verify identity → check E-stop → authorize → revalidate → terminate → verify exit.

**Actual implementation sequence:**
1. E-stop check (initial)
2. Classification check
3. Evidence freshness check
4. Approval token check
5. Protected process check
6. WMI identity revalidation (pid + creationTime + path + name)
7. E-stop re-check (Phase D.1 addition — catches stop activation between initial check and termination)
8. `taskkill /PID <pid> /F`
9. Post-termination verification (WMI query — process should be gone)

**TOCTOU residual window:** between step 6 (identity revalidation) and step 8 (taskkill), the process could exit and its PID could be reused. The post-termination verification (step 9) would detect this: the WMI query would either find a different process (PID reuse detected) or find nothing (exit confirmed). However, the termination command itself would have been sent to the original PID — if the PID was reused between revalidation and taskkill, the wrong process could receive the termination signal.

**Windows-native mitigation (documented, not implemented):** the `NtOpenProcess` + `NtTerminateProcess` sequence with a handle opened at identity-verification time would eliminate the TOCTOU window (the handle pins the process identity). This requires native code (not implemented — task §8 prohibits kernel drivers and the current implementation uses `taskkill`).

**Honest claim:** the implementation detects most TOCTOU scenarios through the post-termination verification, but cannot guarantee atomic identity-check-and-termination without native Windows process-handle pinning.

## 5. Post-termination verification

**Implementation (Phase D.1 addition):** after `terminate()`, the engine queries WMI again to verify the process actually exited. Three outcomes:
1. Process not found → TERMINATED (verified success)
2. Process still found → ACCESS_DENIED (termination didn't work)
3. WMI query error → VERIFICATION_UNAVAILABLE (outcome uncertain — never reported as success)

**Phase D.1 addition:** the `defaultVerifyProcess` now throws on WMI errors (previously it caught errors and returned null, conflating "WMI failed" with "process not found"). This distinguishes genuine termination success from verification failure.

**VERIFICATION_UNAVAILABLE outcome:** added to `ContainmentOutcome` type. When the post-termination verification fails, the result is VERIFICATION_UNAVAILABLE — never TERMINATED. The audit records the uncertainty.

## 6. E-stop integration

**Verified at every containment boundary:**
1. Initial check at `contain()` entry
2. Re-check immediately before `terminate()` (Phase D.1 addition)
3. Concurrent requests: each `contain()` call independently checks E-stop

An active E-stop at any boundary → `REFUSED_E_STOP` or `BLOCK_SYSTEM_UNAVAILABLE`. No approval token can override an active E-stop (the check precedes token validation). The stop state is checked from the E5 `stopKind()` function (durable, not cached).

## 7. E5 audit integrity

**Audit records** for every containment attempt include: event kind (`threat_containment`), outcome, reason, target PID, target name, target creation time, classification, confidence, evidence sources, approval-token presence, timestamp. No secrets, credentials, command lines, or file contents.

## 10. Remaining limitations

1. **No operator identity authentication** — approval tokens prove "someone with launch permission approved" but not WHO approved
2. **TOCTOU residual window** — between identity revalidation and taskkill, Windows does not provide atomic verify-and-terminate for non-admin
3. **Same-user ceiling** — non-admin; elevated/SYSTEM processes cannot be terminated
4. **Transient test failures** — SPF visual live-server (OCR cold start) and E5 M1 recovery pipe (EADDRINUSE) are environmentally flaky
5. **E5 audit chain grows during test campaigns** — test-runner process writes metadata-only entries; recommend KRISHA_SANDBOX_DIR in future test runners
6. **Real E5 audit chain pre-existing line-3 discontinuity** — predates all campaigns; unchanged
